# Placements

## What a placement is

A placement is a named advertising surface. It is a row on the server: a
readable key plus the host surface it belongs to. The key is your own
readable slug — for example `console-workbench` — and you type it into your
own configuration. Nothing else in the codebase carries a key literal of its
own.

The key is:

- **Chosen by you**, when the placement is created on the server, not
  generated by the browser.
- **Unique per publisher** — the same key can be used by different
  publishers on different surfaces, because a key is scoped to the publisher.
- **Stable** — pick it once and keep it stable across deploys. It is part of
  your configuration, not a generated identifier.

## How developers use placement keys

1. Decide which surface in your product will show an ad.
2. Add a placement on the server with a readable key (this is a server-side
   step; this page documents the developer-facing part).
3. Request an ad for that key with `getAd(placementKey)` or
   `render(placementKey, selector)`.

A placement must already exist before any ad can be served for it. A
delivery request for a placement that does not exist is rejected with
`INVALID_PLACEMENT`. A placement that exists but is disabled is answered as
disabled rather than as an ad.

## Placement key facts

| | |
|---|---|
| Pick it once | It is part of your configuration and should not be regenerated. |
| Readable slug | `console-workbench`, `home-feed`, `article-eyebrow` — whatever reads as the surface. |
| Unique per publisher | Scoped to your publisher; another publisher can use the same key on a different surface. |
| Stable | Do not rotate or re-prefix it across deploys. |
| Server owns the mapping | The server resolves the key to the placement row; the browser only sends it. |

There is no `placement: 'choose'` API. A placement either exists or it does
not, and the gateway answers honestly about which one is true.

## Placement states a surface can be in

| State | What it means |
|---|---|
| `loading` | The placement has been requested and the gateway has not answered yet. |
| `ready` | An ad was served and is being watched for viewability. |
| `noFill` | The gateway answered 204: nothing eligible. A normal, successful outcome. |
| `error` | The request failed. Show a fallback and offer to retry. |
| `offline` | Events are queued and replayed when the connection returns. |
| `disabled` | The placement is not configured. No ad is requested. |

A slot should be able to say its honest state: loading, no fill, error,
offline and disabled. Only `loading` and `noFill` are expected outcomes;
`error` and `offline` offer a retry, while `disabled` means the developer
simply omitted the key.

## One placement, one request

`getAd()` is cached for 60 seconds per placement. Two widgets reading the
same placement in the same tick share one delivery request rather than
racing to start two. That means a React StrictMode double-mount or a
re-render does not double-charge an advertiser, and does not double-count
an impression.

`render()` guards against the same thing: it builds the anchor itself and
returns a disposer so the viewability watch can be stopped when the slot is
removed.

## Placements are not campaigns

A placement is a *where*; a campaign is a *what*. The SDK does not own the
campaign mapping — that is resolved server-side from the serve record. Your
page never needs to know which campaign is behind an ad.
